# План реализации консольного Agent Pipeline

План от 13 ноября 2026 года. Этапы 0–6 реализованы для локальных проектов на macOS и Linux.

Выполнено: выделено общее ядро с совместимыми точками входа Orca; реализованы локальный supervisor, SQLite store, отдельные worker-процессы, Pi и Codex CLI adapters, генерация YAML через структурированный инструмент, консольные команды и первый полноэкранный TUI. Самостоятельный прогон трёх Pi-сессий проверен на двух проектах. Прямой Codex CLI также прошёл отдельный smoke-прогон с существующим входом. Этапы 0–6 реализованы в обозначенных ниже границах macOS/Linux и local/current; результаты приведены в отчёте о выпуске.

Уточнение архитектуры по пожеланию пользователя: отдельный облачный аккаунт консоли не нужен. Движок выполняется без LLM; Pi использует profm из действующей конфигурации Cline, а CLI-исполнители — собственные существующие подключения. Pi не является обязательным транспортом для каждого исполнителя.

## Результат

Отдельная команда `pipeline`: пользователь выбирает проект, описывает задачу, получает самостоятельно составленный сценарий, настраивает шаги и наблюдает за несколькими агентами в терминале. Программа работает без запущенного Orca. Плагин Orca остаётся вторым интерфейсом к общему движку и формату сценария.

Основа — TypeScript и Pi SDK. Модель планировщика составляет и изменяет план через инструменты; зависимости, запуск, повторы, подтверждения и финальные статусы определяет движок. Первая версия исполняет локальные шаги в отдельных сессиях Pi. Настоящие Codex/Kimi/OpenCode CLI доступны через Orca, прямой внешний адаптер реализован для Codex; выбор модели внутри Pi не выдаётся за запуск другого CLI-агента.

## Пользовательский поток

1. **Проект и задача.** Текущая папка или сохранённый проект; показан полный путь. Пользователь описывает цель. Planner исследует проект, предлагает шаги и сохраняет валидный `.agent-pipeline/plans/*.pipeline.yaml`.
2. **Шаги и агенты.** Слева список зависимостей, справа настройки выбранного шага. Видны исполнитель, модель, входные отчёты, проверки результата, подтверждения и разрешённая цепочка fallback. Можно добавить шаг, связать его с другим, удалить связь, изменить порядок через зависимости и открыть YAML в `$EDITOR`.
3. **Запуск и наблюдение.** Слева шаги со статусами, справа события выбранного исполнителя и его результат. Доступны пауза планирования, продолжение, отмена, ответ агенту, подтверждение, смена исполнителя и повтор упавшего шага.

Назад и вперёд сохраняют черновик. Переход к запуску требует валидного плана и успешного preflight. После запуска используется неизменяемый снимок сценария с хешем; правки черновика относятся к следующему запуску. Переключение выбранного шага не запускает его. После ручного выбора слежение за активным шагом включается отдельной командой.

В узком терминале список и подробности показываются последовательно. Полноэкранный просмотр доступен для журнала, настроек и YAML. Терминальная версия редактирует связи списком зависимостей; существующий граф Orca сохраняет перетаскивание карточек и рисование линий.

## Архитектура и перенос существующего кода

Целевая структура добавляется постепенно, без одномоментного переноса всего плагина:

```text
packages/core/          схема, DAG, состояния, scheduler, policies, события
packages/runtime/       supervisor, локальное хранилище, IPC, recovery
packages/pi-adapter/    запуск отдельных Pi-сессий и нормализация событий
packages/terminal/      команда pipeline, агент-планировщик, TUI
src/                   host Orca: panels, editor, worker, Orca adapter
```

| Текущий код | Изменение |
| --- | --- |
| `src/scenario.ts`, `src/editor.ts`, `src/types.ts` | Выделить общий формат, графовые операции и типы; сохранить чтение существующего YAML и `layout` |
| `src/coordinator.ts` | Отделить scheduler и политики от конкретного `OrcaClient`; сохранить сериализацию tick/control |
| `src/planner.ts` | Отделить инструкции, проверку и сохранение плана от транспорта Orca |
| `src/capacity.ts`, `src/quota.ts`, `src/failover.ts`, `src/metrics.ts` | Перенести переносимую логику; источники usage и ошибок оставить адаптерами |
| `src/cli.ts` | Сохранить Orca-адаптер; request receipts и terminal handles остаются его деталями |
| `src/mutations.ts`, `src/artifacts.ts` | Использовать контракты журнала и артефактов; добавить транзакционный локальный store |
| `src/worker.ts` | Оставить интеграцию с host API, настройками и storage Orca |
| `src/beads.ts`, `src/pr.ts` | Сделать необязательными интеграциями; их отсутствие не мешает базовому запуску |

Контракты ядра: `ExecutionBackend`, `RunStore`, `EventSink`, `ApprovalStore`, `ProjectResolver`, `UsageReader`, `ArtifactStore`. Backend предоставляет capabilities, preflight, старт с operation ID, наблюдение, отправку сообщения, отмену и reconciliation. У каждого backend явно указаны возможности восстановления, размещения и владения процессом.

Локальные Run/Task/Gate больше не требуют объектов Orca. В Orca-режиме backend хранит соответствие локальных идентификаторов нативным Run/Task/Dispatch. Старые записи плагина читаются через версионированный адаптер; исходные данные не перезаписываются без проверки миграции.

## Этапы и критерии готовности

### 0. Проверить Pi и зафиксировать границу MVP

- Зафиксировать точную версию SDK, совместимый Node и lockfile. Сверить действующие exports и события с документацией установленной версии.
- Проверить три независимые сессии, поток событий инструментов, сохранение/загрузку контекста, отмену, ошибку авторизации и окончательное завершение. Для завершения учитывать settled-состояние; один `agent_end` недостаточен.
- Запустить исполнителя в отдельном дочернем процессе, проверить его остановку и возможность восстановления сессии после сбоя. Выбрать поддерживаемый SQLite-драйвер и терминальные компоненты Pi по результатам этого прототипа.
- Описать capabilities MVP: local/current, Pi-сессии, последовательные и параллельные зависимости, ручные подтверждения. Неподдерживаемые placement/исполнители отклоняются до старта.

**Готово:** воспроизводимый smoke-пример, записанная версия зависимостей и подтверждённые lifecycle-контракты. Учётные данные настраиваются средствами Pi, отдельно от Orca.

### 1. Выделить общее ядро и сохранить работу плагина

- Ввести контракты backend/store, заменить зависимость Coordinator от конкретного класса.
- Вынести нормализацию состояний и идентификаторов; Orca-специфичные поля убрать из доменных решений.
- Перенести чистые проверки сценариев и scheduler-тесты на независимый Node test runner. Тесты panels/host остаются в `orca/testing`.
- Обновить сборку плагина: общий код должен попадать в release, без неявной зависимости от monorepo или внешнего `node_modules`.

**Готово:** общий движок запускает тестовый backend без Orca; существующие проверки плагина, typecheck, release build и validate проходят; старые YAML и сохранённые запуски читаются.

### 2. Сделать headless runtime с надёжным состоянием

- Один supervisor-процесс владеет запуском; клиенты подключаются локально через IPC. SQLite хранит операции, события, снимки состояния и подтверждения транзакционно в игнорируемом runtime-каталоге проекта.
- Добавить версии схемы, последовательные event IDs, восстановление подписки после разрыва и блокировку второго writer. Клиентские повторы имеют устойчивые request IDs.
- Перед внешним запуском записывать intent; затем receipt. После сбоя сверять operation ID, session ID и владение процессом. Не обещать exactly-once для неподдерживающего это внешнего backend.
- При неизвестном результате блокировать повтор соответствующего шага до reconciliation. PID без проверки принадлежности не используется для отмены.
- Пауза запрещает новые старты; уже работающие шаги продолжаются. Отсоединение TUI сохраняет supervisor. После перезагрузки компьютера восстановление выполняется при следующем `resume`; автоматический системный сервис в MVP не требуется.
- Решение manual approval принадлежит пользователю. Планировщик может запросить подтверждение и объяснить его, но не разрешает собственный gate. Runtime проверяет происхождение решения независимо от интерфейса.

**Готово:** закрытие клиента и повторный attach не создают новых попыток; после падения supervisor завершённые шаги не повторяются, неизвестные старты показаны явно.

### 3. Подключить Pi и получить первый самостоятельный прогон

- Отдельный процесс и контекст сессии на попытку; нормализовать события запуска, активности, ожидания пользователя, результата, ошибки и отмены.
- Разделить исполнителя, provider и model. Лимиты параллельности учитывать по реальному provider, а не только по названию роли.
- Planner вызывает структурированный инструмент предложения плана; ядро проверяет схему и DAG, сериализует YAML и сохраняет файл атомарно. Невалидный ответ возвращается planner для исправления с ограничением попыток.
- Предшествующие результаты передавать как явно перечисленные артефакты. Reviewer получает новую сессию и самостоятельное задание.
- Принимать успех только после завершения агента, записи результата и выполнения acceptance-проверок с фактическими exit codes. Проверки исполняет runtime в выбранном проекте.
- Соблюдать command policy в доступных инструментах и проверках; `readOnly` сам по себе не считается изоляцией ОС. MVP использует контролируемые инструменты; более сильная изоляция — отдельная возможность.
- В одном checkout сериализовать шаги, способные менять исходники. Параллельные изменения разрешать после появления изолированных worktrees; перед независимым ревью фиксировать проверяемый снимок и прекращать конкурирующие записи.

**Готово:** через headless CLI выполняется `анализ → приоритеты → независимое ревью` в трёх Pi-сессиях, без Orca и `bd`, с отчётами и результатами проверок на диске.

### 4. Реализовать консольного агента и TUI

- Добавить команды `pipeline`, `plan`, `validate`, `run`, `status`, `attach`, `pause`, `resume`, `stop`, `approve`, `retry`, `doctor`; машинный режим `--json` отделить от TUI.
- Использовать Pi SDK для диалога с инструментами plan/inspect/update/status/control. Все изменения исполняются через runtime с той же валидацией, что в обычных командах.
- Реализовать три этапа потока, клавиатурную навигацию, зависимости, журнал выбранного исполнителя и историю попыток. Для блокировок показывать точную причину и доступное действие.
- Отображать последнее подтверждённое событие и его время. Тишина в журнале не означает падение или успешную работу. Анимация запуска не заменяет наблюдение.
- Разделить действия: прервать текущий ввод/планирование, отсоединиться от запуска и остановить весь запуск. При detach явно показать команду возврата.

**Готово:** весь сценарий от выбора проекта до трёх отчётов выполняется через TUI; интерфейс проверен на узком и широком терминале, при resize, длинном выводе и ожидании ответа пользователя.

### 5. Добавить Orca и других исполнителей

- Подключить Orca backend к консольному клиенту: доступные проекты, видимые native workers, переход в окно, нативные approvals и восстановление receipts.
- Ввести явную конфигурацию маршрута: backend, executor, provider, model, capabilities. Существующее `agent: codex` сохраняет смысл; для самостоятельного backend требуется явное сопоставление, без скрытой подмены Pi-сессией.
- Общий YAML редактируется обоими интерфейсами с проверкой версии/хеша при записи. Один запуск имеет одного владельца: второй интерфейс подключается к нему, а не заводит второй scheduler. Одновременное управление требует IPC-моста и проверяется отдельно.
- После Orca добавить один прямой внешний адаптер по поддерживаемому SDK/RPC/ACP. Каждый следующий проходит общий набор contract-тестов; наличие ACP у конкретного агента проверяется отдельно.
- Fallback разрешён только по указанной цепочке и классифицированной ошибке; показывать причину, прежнего и нового исполнителя, checkpoint и номер попытки. При неизвестном старте, отсутствии вывода или обновлении CLI fallback не запускается автоматически.

**Готово:** консоль управляет реальным Orca-прогоном, исполнители видны в Orca; переходы между агентами прослеживаются, повторное подключение не дублирует задачи. Прямой внешний адаптер имеет отдельный подтверждённый E2E.

### 6. Условия по результатам и выпуск

- Ввести версионированные структурированные результаты и ограниченные декларативные условия. Сравнивать типизированные поля результата; произвольный JS/shell в условии не исполнять.
- Определить семантику веток, joins, отсутствующих полей, `skipped` и итогового прогресса. Старые `needs` продолжают означать успех всех предшественников. Поддержку нового формата согласованно добавить в Orca editor и TUI.
- Упаковать CLI для чистой установки; проверить отсутствие зависимости от каталога разработки и Orca, диагностику аккаунтов, обновление схемы состояния и документацию восстановления.
- Выполнить ручной E2E в тестовом проекте, воспроизвести сбои, сохранить отчёты и доказательства состояний.

**Готово:** подтверждённая матрица проверок ниже, инструкция установки и воспроизводимый демонстрационный сценарий.

## Проверки, обязательные для выпуска

| Проверка | Ожидаемое поведение |
| --- | --- |
| Цикл, неизвестная зависимость, невалидный YAML | Запуск отклонён до создания исполнителей; черновик сохранён |
| Три независимых контекста и передача отчётов | Reviewer получает артефакты, сохраняя отдельную историю |
| Параллельные ветки и provider limits | Активных исполнителей не больше заданного лимита |
| Manual approval | Зависимый шаг не стартует до решения; повторное решение идемпотентно |
| Агент закончил, acceptance завершилась ошибкой | Шаг не становится успешным |
| Нет новых событий или оборвался поток | Видно устаревшее наблюдение; скрытого fallback нет |
| Неизвестный старт, повтор запроса, поздний receipt | Повторного исполнителя нет до reconciliation |
| Quota, обычная ошибка, нет авторизации | Различимые причины и разные правила восстановления |
| Pause/retry/cancel одновременно с событиями | Согласованное конечное состояние без повторных стартов |
| Закрытие TUI, падение supervisor, перезапуск ОС | Честное восстановление; завершённая работа не повторяется |
| Два клиента одного запуска | Один writer/scheduler; управляющие операции сериализованы |
| Несовместимый placement/backend | Явная ошибка preflight без скрытого local fallback |
| Условия и joins | Проверены обе ветки, пропуски и отсутствующие поля результата |
| Чистая установка CLI и release плагина | CLI работает без Orca; плагин проходит прежние host-проверки |

Contract- и fault-injection-тесты используют детерминированный backend. Реальные Pi/Orca E2E выполняются отдельно с доступными аккаунтами. Отсутствие аккаунта отмечается как непроверенная интеграция, а не успешный тест. Политика логов и редактирование артефактов проверяются на тестовых секретах; credentials не копируются между провайдерами.

## Порядок поставки

1. **Первый инкремент: этапы 0–3.** Самостоятельный headless-прогон трёх Pi-агентов с отчётами и восстановлением. Это первая проверка всей архитектуры на реальной работе.
2. **Второй инкремент: этап 4.** Полный терминальный пользовательский поток поверх того же runtime.
3. **Третий инкремент: этап 5.** Orca и проверенные внешние исполнители; общие сценарии и наблюдение.
4. **Четвёртый инкремент: этап 6.** Ветвления по данным, проверка упаковки и выпуск.

Каждый инкремент заканчивается исполняемым примером, результатами проверок и списком реально поддерживаемых возможностей. Сроки уточняются после проверки SDK и recovery на этапе 0.
